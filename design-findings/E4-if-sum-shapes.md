# E4 — What grammar would `IF` and `SUM` actually need?

Everything below was run. Harness: `experiments/E4-if-sum/`
(`scan.py`, `dump_noteval.py`, `classify.py`); raw counters and samples in
`experiments/E4-if-sum/out/`. Corpora are E1's, unchanged.

---

## 0. Verdict up front

**`SUM` should not be added to §4.2 as a grammar feature, because 99.1% of the
corpus cells that "need" it are already generated by §4.2 today.** What is
missing is a translator, and behind the translator one real semantic question
that `SUM` has been standing in for all along: **blanks.**

**`IF` should be added, but only its numeric-branch form, and that is 52.3% of
`IF` cells rather than all of them.** The other 47.7% do not need a bigger
grammar — they need a bigger *value model*, which is a different and much more
expensive change.

Together the two admit **12,501 of the 21,165 NOTEVAL cells (59.1%)** with no
change to what a computed cell is allowed to hold.

## 1. What was measured, and why the obvious measurement is wrong

E1 established that 21,165 corpus cells translate onto `.mdtbl`'s surface and
then fall outside §4.2, and that `IF` (12,643) and `SUM` (5,552) are 86% of
them. That says which function names appear. It does not say what grammar would
compute them.

A first pass scanned raw `<f>` text across all 5,458 SB912 workbooks and all 68
TmplEnron workbooks. **That measurement is misleading and is not used for any
conclusion here.** TmplEnron alone contributes 798,664 `IF` calls, every one of
the shape

    IF($C$6<='Apr 2001'!Q12, 'Apr 2001'!A12, 0)

— a cross-sheet absolute-reference pull, which is `UNTRANSLATABLE` in E1's
ladder and never reaches §4.2 at all. E1's own counters confirm it: TmplEnron
has **no `NOTEVAL` bucket whatsoever**; all 21,165 are SB912's. Designing a
grammar against raw corpus frequency would have designed it for formulas that
cannot arrive.

The figures below are therefore taken from E1's **post-translation** `NOTEVAL`
expressions. E1 keeps 40 of them; `dump_noteval.py` re-runs E1's own pipeline
with the cap lifted and captures all **21,165**, matching E1's counter exactly.

## 2. `SUM` — a translator gap wearing a grammar gap's clothes

    5,912  NOTEVAL cells whose expression calls SUM
    5,849  ... where SUM is the ONLY thing blocking evaluation

    3,485  SUM(a, b, c)      a comma list of column names
    2,376  SUM(col)          one whole column
       51  anything else

Both of the large shapes are **already expressible in `.mdtbl` today**:

| corpus shape | `.mdtbl` today |
|---|---|
| `SUM(A, B, C, D, E)` | `| t = A + B + C + D + E |` — §4.2 `expr`, unchanged |
| `SUM(Tier_1, Tier_2, Tier_3)` | `| t = Tier_1 + Tier_2 + Tier_3 |` |
| `SUM(Total)` | `grand := sum(Total)` — a §7 declaration, not a row formula |

**5,861 of 5,912 (99.1%) need no new grammar.** Adding a variadic row-wise `sum`
purely to spell these would be a second spelling of `+`, which §4.1.6 and §4.2
rule 7 both argue against at length, and it would earn nothing.

The single residual shape is worth showing because it is the whole tail:

    SUM(IF((A="A")+(D="D")+…,1,0))

an array-formula idiom, which E1 excludes upstream anyway.

### 2.1 …except for the thing `SUM` was really carrying

`SUM` and `+` are not the same function on real data. **`SUM` skips blanks; `+`
does not.** In `.mdtbl` a blank operand is `#REF!` by §8 — deliberately, under
I3 (loud failure). And that difference is not a corner case: it is **the single
largest disagreement class E1 found**, 9,321 cells in SB912 and 7,632 in
TmplEnron, **30.4% of all 55,681 comparisons**, every one of them a cell where
Excel had a number and rowspec correctly refused to invent one.

So the honest statement is that `SUM` was never the missing feature. The missing
feature is **a way for an author to say "add what is present" and be understood
by every reader** — as against `+`, which says "all of these must be present".
Those compute different values on the same table, so it is not a second
spelling; it is the capability §8 currently lacks a syntax for.

This is the same question E1 deferred as *"`#REF!(name)` conflates a name that
does not exist with a name whose cell is blank"*. **It is one question, not
two**, and `SUM`, `IF(x="", …)` and that deferral are three faces of it.

## 3. `IF` — half of it is cheap, and the half that is not is a value model

    12,697  NOTEVAL cells whose expression calls IF

     6,640  CHEAP     numeric branches, one comparison, arity 3   (52.3%)
     6,057  EXPENSIVE                                             (47.7%)
             5,943  a branch returns something that is not a number
               491  the condition chains several comparisons
               440  the condition calls a function (AND/OR/ISBLANK/…)
                24  arity is not 3

The cheap set is homogeneous and its samples are unremarkable:

    IF(Impressive_Splash_page__Y_N="Y", 1, 0)
    IF(Quantity<>0, 1, 0)
    IF(Amount>0, 0, Bills)
    IF(WITHOUT_PRESS="", PCS_MTR, 0)
    IF(Office_1="", Assigned_employee_2023, Office_1)

Condition right-hand sides across all `IF` cells: **string 8,404, number 3,654,
name 121, expression 9.** A comparison against a string literal is the majority
case, and §4.2 rule 6 already fixes exactly those semantics for `where`
predicates — *"Equality compares text, never numbers"*, NFC, trimmed, unescaped.
Reusing that rule for a condition costs no new decision.

The expensive set is expensive for one dominant reason: **a branch returns a
string.** `IF(…, "PASS", "FAIL")` requires a computed column to hold text, which
changes what `sum` over that column means, what a `where` predicate compares
against, what §10 canonicalises, and what §9's refusals check. That is a value-
model change and it should be proposed on its own evidence, not smuggled in as
part of adding a function.

Note the last two cheap samples. `IF(x="", fallback, x)` is how a spreadsheet
spells *"if blank, use this instead"* — so the blank question of §2.1 surfaces
inside `IF` as well, from the other side.

## 4. What this changes about the roadmap

The claim I made before measuring — *"close `IF` and `SUM` in §4.2, they are
17,952 of the 21,165 cells outside the grammar"* — was arithmetic on E1's
function-name counters and it does not survive contact with the expressions.
Corrected:

| | claimed | measured |
|---|---|---|
| cells `SUM` would admit | 5,552 | **51** (5,861 are already expressible) |
| cells `IF` would admit | 12,643 | **6,640** (6,057 need a value model) |
| total, no value-model change | 17,952 | **12,501** |

12,501 of 21,165 is still 59.1% of the gap and it is worth having. But the two
features are not peers, the work is not where the names said it was, and the
interop ceiling does not move as far as claimed.

## 4a. Verified against the real parser, not against the classifier

§§2–3 classify expressions with regexes, and a regex prediction about a grammar
is a guess. Every one of the 21,165 NOTEVAL expressions was therefore fed
through rowspec's **actual §4.2 parser** after the one mechanical rewrite the
Excel surface needs (`IF(` → `if(`; function names are case-insensitive in
Excel and lowercase in §4.2). Harness: `experiments/E4-if-sum/accept.py`.

    21,165  NOTEVAL expressions
     6,655  ACCEPTED by the parser with `if` implemented
     6,640  ... predicted by the regex classifier   (0.2% apart)

     6,655  of which carry an `if`
         0  of which do not

**The parser agrees with the classifier to within 0.2%, and `SUM` contributes
exactly zero.** That is §2's claim demonstrated rather than argued: the corpus
`SUM` cells are still refused after `if` lands, because what they needed was
never a grammar.

Applying the translator rewrite §2 says they need — `SUM(a, b, c)` → `(a+b+c)`,
purely mechanical, no new syntax anywhere:

    accepted, if() alone                 6,655
    accepted, if() + the SUM rewrite    12,168
    gain attributable to the rewrite     5,513   with NO grammar change

12,168 of 21,165 is **57.5%** of the gap, against §4's static prediction of
59.1%.

What still blocks the remaining 8,997, by the function responsible:

    6,030  IF          the text-returning half -- a VALUE-MODEL change (§3)
    2,052  ROUNDDOWN
      921  ROUND
      621  INT
      545  MIN
      351  AND
      197  OR
      192  AVERAGE
      186  CEILING
       41  MAX

`ROUNDDOWN` at 2,052 did not appear in E1's function tally at all, because there
it was nested inside expressions counted under another name. It is now the
largest single blocker after `IF` itself, and it is the kind of thing only this
measurement surfaces.

**One caveat, stated because it is the difference between two claims.** This is
an *acceptance* measurement: the parser admits 12,168 expressions. It is not a
differential — nobody has yet checked that the values rowspec computes for them
match the values Excel cached. Confirming that needs E1's grammar check
replaced, because E1 decides evaluability by parsing the translated expression
as **Python**, and `IF(a="x",1,0)` is not valid Python at all (it reads `a="x"`
as a keyword argument, which is why 10,959 of these cells are bucketed
`not-python:IF` rather than `Call:IF`). Until that run happens the honest claim
is "the grammar admits them", not "the evaluator gets them right".

## 5. Method note: the tenth instance

E1's harness carries a mutation control — `E1_MUTATE` injects a known defect and
the differential must collapse — because a differential that cannot fail is
worthless. It was keyed on `RT.OPS[pyast.Add]`, from when the evaluator
delegated to `ast.parse`. It no longer does. `RT.OPS` is keyed on `'+'` now, so

    RT.OPS[pyast.Add] = operator.sub

installed a dead dictionary key named `Add` and `+` went on adding. The mutant
would have run the full differential, reported total agreement, and been read as
*"the harness is sound"* when it meant *"the mutation never fired"*. The
`blank-is-zero` mutant was dead the same way: it tested `isinstance(node,
pyast.Name)` against nodes that are now `RT.Name`.

**This is the tenth time in this project that a check which could not fail
reported a pass.** Each mutant now asserts that it changed something before the
run starts, and that assertion was itself tested by breaking it.


## 6. What the adversarial pass found, and what it cost the spec

The conformance author for rule 10 was forbidden to read `reference/` and wrote
102 cases from `SPEC.md` alone. Two independent halves were commissioned at the
same time and neither could see the other: I wrote 8 mutants against rule 10's
`[CHOICE]`s without seeing any case, and the cases were written without seeing
the implementation. **Their cases killed 7 of my 8 mutants.** The survivor —
a cycle closing only through a `comparison`'s `ident` — I confirmed was real,
then reported only the *area* rather than the input, and they closed it from
the prose with a two-column cycle. A self-cycle does not catch it, because
re-entry detection finds that one with no dependency graph involved.

**One live defect in the implementation.** `if(nope = "", 1, 0)` on a column
that does not exist returned `1.0`. The cell lookup was `env.get(name, "")`,
which is one sentinel for "this cell is blank" and "there is no such column", so
the same missing column was an error under `= 0` and a blank under `= ""`. A
transposed letter in a column name turned "use this when that is missing" into
"always", in every row, with no diagnostic — §8's "a broken reference never
evaluates to zero, empty, or a stale value", violated by the empty case.

**One construct with two readings and no rule.** `if(total = "20", 1, 0)` over a
*computed* `total`: §9.22 did not reach it (scoped to `where` predicates),
§9.20 did not (the grammar generates it), and both readings produce a number.
Measured, this implementation renders `20.0` and matched nothing in any row; a
reader rendering `20` matches every row. §9.22 now covers it. The author
declined to write a case for it, correctly — "writing one would be inventing the
answer."

**Two defects in the prose.** `if(a > -1, 1, 0)` was unwritable, because
`literal` is unsigned and `order-rhs` had no `factor`; a new `signed` production
fixes it. And §8 asserted "exactly three `#REF!` shapes" while §4.2 rule 2 had
required a fourth since the arithmetic model landed — the drift a document
acquires when a rule is added in one section and counted in another.

**Six further ambiguities**, each closed by a sentence: function names are
case-sensitive (`IF(` is what a spreadsheet export emits, and admitting it makes
a table holding both `if` and `IF` unanswerable under rule 4); an error operand
is an error under `=` and `<>` too, and not blank, or a `#REF!(/0)` becomes the
author's missing-data fallback; a `cond`'s parenthesis counts toward §9.23's 64;
and rule 7 now names `order-rhs` and `eq-rhs` among the operand positions.

**One decided against the case that asserted it.** An unselected branch naming a
column that does not exist: the case asserted the lazy reading, and rule 10 now
takes the static one. The line is between the **header** and the **data** —
whether `nope` resolves is knowable before a row is read and identical in every
row, while whether `b` is zero in `if(c > 0, a / b, 0)` is not, so `#REF!(/0)`
stays per-row and this rule does not touch it. Under the lazy reading a column
is well-formed until a merge adds the first row that takes the other branch, and
then that column and every aggregate over it are poisoned by a commit touching
no formula and no header.

Final: **58 mutants killed, 0 survived, 1 equivalent, 0 stale.**
